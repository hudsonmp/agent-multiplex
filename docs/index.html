agent-multiplex

Drive claude and gemini side-by-side in parallel git worktrees on the same repo. One browser tab, two PTYs, raw transcripts on disk. Built so you can give two agents the same task and see where they actually diverge.

how it's hosted

The UI lives at a public URL. The agents themselves run on your Mac — they need access to your filesystem, your installed CLIs, and your API keys, none of which should travel to a server. The browser connects directly to your local backend; nothing in this app sees your keys or repos except your own machine.

hosted UI
Open the app in your browser. Static SPA, no account, no signup.
your Mac
Run the backend locally with one command. It spawns the agent PTYs and serves them to the hosted UI over http://localhost:4040.

run the local backend

$ git clone https://github.com/hudsonmp/agent-multiplex.git
$ cd agent-multiplex
$ npm install                # compiles node-pty natively
$ npm run dev -w backend     # listens on :4040

Requires Node 20+ and git. On macOS, node-pty's build needs xcode-select --install.

The hosted UI polls localhost:4040 every few seconds. When the backend is running, the status indicator flips to backend online and the launch form unlocks.

claude
Anthropic's Claude Code. Install per docs.claude.com.
gemini
Google's open-source gemini-cli: npm i -g @google/gemini-cli.
graceful degradation If only one binary is on $PATH, the missing pane shows exited (127) and the rest of the session runs normally. You can evaluate the harness before installing both.

api keys

The launcher form has optional fields for ANTHROPIC_API_KEY and GEMINI_API_KEY. They're stored in your browser's localStorage and sent only to your own local backend, which injects them as env vars into the spawned PTYs. Leave them blank to fall back to whatever auth the CLIs already have on your machine (e.g. claude auth login, or GEMINI_API_KEY in your shell).

how it works

Three design choices do most of the work. Each is non-obvious enough to be worth stating before you use the tool, because they're what makes the comparison faithful.

PTYs, not pipes

Both claude and gemini detect when stdout is attached to a real terminal. If they see a pipe, they collapse to a degraded mode — no cursor positioning, no live progress, sometimes a different output format entirely. To see what the agent actually shows a human user, the harness allocates a pseudo-terminal per agent via node-pty and streams raw bytes — ANSI escapes, cursor moves, UTF-8 box-drawing — over a websocket to xterm.js in the browser. The browser pane is byte-equivalent to running the CLI in your own terminal.

Worktrees, not clones

Both agents work the same repo at the same time, so they need filesystem isolation. The harness creates two git worktrees per session — <repo>-mux-claude-<id>/ and <repo>-mux-gemini-<id>/ — each on its own branch off your base. Worktrees share the parent repo's object database, so this is nearly free in disk and bandwidth, but each working tree is independent: claude editing foo.py doesn't touch gemini's foo.py. Closing the session removes the worktrees; the branches stay so you can diff or merge after.

Bytes, not events

Transcripts are saved as raw PTY output, with \x1e<unix_ms>\x1e markers inserted between chunks. Not a structured event log, not a recording of "tool calls" — the actual bytes the agent printed, including thinking, errors, and TUI redraws. This is more verbose but doesn't lose information: any structured analysis you'd want later can be derived from the bytes, but the inverse isn't true. The \x1e Record Separator was picked because it never appears in ANSI escape sequences, so timestamps strip cleanly with a one-line regex.

run a session

  1. In the repo field, paste either an absolute local path (/Users/you/your-project) or a GitHub URL (https://github.com/foo/bar). URLs are cloned to ~/.agent-multiplex/repos/<owner>__<repo>/ on first use and refreshed thereafter. Click load branches.
  2. Pick a base branch. The default agent branches (mux/<agent>-<timestamp>) are fine — they keep harness branches clearly out-of-band from your normal work.
  3. (Optional) Enter API keys.
  4. Launch. Two worktrees are created; each agent boots in its own.
  5. Type into either pane. Drag the divider. Browser resize reflows both terminals.
  6. Close the session: PTYs are killed, worktrees removed, manifest sealed with closed_at. Branches and logs are preserved.

comparing the two agents

The point of running both is to see where they diverge — agents that produce the same answer on easy tasks can still differ wildly on the path they take to get there, and the divergence is where the interesting signal lives. A few lenses to apply when reading a session:

01tool-call grain

How many discrete reads / edits / shell invocations does each agent make? One agent might read three files and rewrite one; the other might read one and make ten small edits. Finer grain is often slower but recovers from mistakes more locally.

02plan visibility

Does the agent state a plan before acting, or does it act and then summarize? Stated plans are easier to interrupt; implicit plans are faster but harder to redirect mid-task.

03recovery from being wrong

Make one agent guess at something it can't know (e.g. a function signature you haven't shown it). Watch how it reacts when reality contradicts the guess. Some agents double down; some retreat and re-read; some ask. The recovery shape is more revealing than the failure itself.

04prompt-following vs latitude

Give a slightly-underspecified task. Does the agent execute literally on what you said, or fill the gaps with its own judgment? Both can be right; the question is which you want when. Side-by-side makes the difference visible in a way solo runs don't.

05final diff shape

Once both are done, diff what they actually committed (commands below). Sometimes the transcripts look similar but the diffs are wildly different. Sometimes the transcripts diverge but converge on equivalent code. Both are worth knowing.

operational verbs

# list session artifacts
$ ls ~/.agent-multiplex/sessions/<id>/
manifest.json   claude.log   gemini.log

# replay a transcript with timestamps stripped
$ cat claude.log | perl -pe 's/\x1e\d+\x1e//g'

# diff each agent against the base branch
$ git -C <repo> diff main..mux/claude-<timestamp>
$ git -C <repo> diff main..mux/gemini-<timestamp>

# diff the two agents directly
$ git -C <repo> diff mux/gemini-<timestamp>..mux/claude-<timestamp>

good first comparisons

Tasks where divergence is likely and instructive:

  • Underspecified refactor — “Make this function easier to test” on a non-trivial function. Tests the latitude vs literalism axis.
  • Failing test — Hand them a failing unit test and the file it tests. The recovery path differs sharply across agents.
  • Same prompt, dirty repo — Run with uncommitted changes already in the base branch. Watch which agent notices.
  • Build error you can fix two ways — A type error with either an upstream fix or a downstream cast. Which one each agent picks tells you something about its priors.

notes & limits

  • Server binds to 127.0.0.1. No auth. Single-user, single-laptop.
  • The spawned subprocess inherits a sanitized PATH from npm, so the server explicitly augments it with ~/.local/bin, ~/.npm-global/bin, /opt/homebrew/bin, and the usual system dirs. If your CLI lives somewhere else, symlink it into one of those.
  • If the backend dies mid-session, worktrees outlive it. Clean up with git worktree list then git worktree remove --force <path>.
  • Closing a session does not delete branches. Drop them with git branch -D mux/<agent>-<timestamp>.
  • PTYs die with the backend process — there is no daemon to reattach to. A future iteration could persist sessions through restarts.
