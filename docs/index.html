agent-multiplex

Drive claude and gemini side-by-side in parallel git worktrees on the same repo. Two PTYs in your browser, raw transcripts saved locally. Built so you can give two agents the same task and see where they actually diverge.

app: agent-multiplex-production.up.railway.app  ·  source: github.com/hudsonmp/agent-multiplex

how it's split

The UI lives at a public URL; the agents run on your Mac. Your repo, your API keys, and the spawned claude / gemini processes never leave your machine. The hosted page polls http://localhost:4040 every few seconds and flips to online when it finds the backend you started locally.

hosted UI
The page you're on. Static React bundle, no account, no signup. Lives on Railway.
your Mac
The backend. Spawns PTYs, runs git worktree, writes transcripts to ~/.agent-multiplex/sessions/.

Chrome's secure-context rule lets the HTTPS page reach http://localhost without mixed-content blocking, so no proxy or local certs are needed.

full setup

Maybe 5 minutes end-to-end if you already have a Node toolchain. Numbered so you can copy-paste in order.

  1. System prerequisites

    Node 20 or newer, git, and (on macOS) Xcode command-line tools, which node-pty's native build needs.

    $ node --version          # v20.x or newer
$ git --version
$ xcode-select --install   # macOS only, skip if already installed

    On Linux: apt install build-essential python3 instead of the Xcode line.

  2. Install the two agent CLIs

    You can run the harness with only one installed — the missing pane will show exited (127) and the rest of the session works normally. But to actually compare them you want both.

    # Claude Code (Anthropic)
$ npm i -g @anthropic-ai/claude-code

# gemini-cli (Google, open source)
$ npm i -g @google/gemini-cli

    Verify both are on $PATH:

    $ which claude
$ which gemini

    If either is missing, see docs.claude.com or github.com/google-gemini/gemini-cli.

  3. Authenticate each CLI (or supply keys in the UI)

    Two ways to give the CLIs access to their APIs:

    • Use the CLI's own auth. Run claude once and follow its login flow. For gemini: export GEMINI_API_KEY=… in your shell. The harness inherits these.
    • Paste keys into the launcher form. The UI has fields for ANTHROPIC_API_KEY and GEMINI_API_KEY. They're saved to your browser's localStorage and sent only to your local backend, which injects them as env vars when spawning the PTYs.

  4. Clone and install the harness

    $ git clone https://github.com/hudsonmp/agent-multiplex.git
$ cd agent-multiplex
$ npm install

    The install compiles node-pty natively. First run takes ~20 seconds; subsequent installs are fast.

  5. Start the local backend

    $ npm run dev -w backend

    You'll see Server listening at http://127.0.0.1:4040. Leave this running — it's the process that spawns the agents.

  6. Open the hosted UI

    Open agent-multiplex-production.up.railway.app. Within a few seconds the status line at the top should flip from checking to online. The launch session button unlocks.

  7. Launch a session

    In the repository field, paste either:

    • an absolute local path (e.g. /Users/you/your-project), or
    • a GitHub URL (e.g. https://github.com/foo/bar) — cloned on first use to ~/.agent-multiplex/repos/<owner>__<repo>/.

    Click load branches, pick a base, accept the auto-generated agent branch names, paste keys if you skipped step 3, then launch session →. Two git worktrees are created off the base branch, one PTY spawns in each, and the split-pane view opens.

  8. Drive both panes

    Click into either pane and type. Drag the divider to rebalance. Browser resize reflows both terminals. Same prompt in both panes is the basic move.

  9. Close cleanly

    Click close session. PTYs are killed, both worktrees are removed (git worktree remove --force), the manifest is sealed with closed_at. Branches and log files stay so you can diff later.

how it works

Three design choices do most of the work. Each is worth knowing before you use the tool, because they're what makes the comparison faithful.

PTYs, not pipes

Both CLIs detect whether stdout is a real terminal. Piped, they collapse to a degraded mode — no cursor positioning, no live progress, sometimes a different output format entirely. The harness allocates a pseudo-terminal per agent via node-pty and streams raw bytes (ANSI escapes, UTF-8 box-drawing, cursor moves) over a websocket to xterm.js. The browser pane is byte-equivalent to running the CLI in your own terminal.

Worktrees, not clones

Both agents work the same repo at the same time, so they need filesystem isolation. The harness creates two git worktrees per session at <repo>-mux-claude-<id>/ and <repo>-mux-gemini-<id>/, each on its own branch off your base. They share the parent repo's object database — nearly free in disk — but the working trees are independent.

Bytes, not events

Transcripts are saved as raw PTY output with \x1e<unix_ms>\x1e markers between chunks. Not a structured event log, not a recording of "tool calls" — the actual bytes the agent printed, including thinking, errors, and TUI redraws. Any structured analysis can be derived from the bytes; the inverse isn't true. The \x1e Record Separator was picked because it never appears in ANSI escape sequences, so timestamps strip cleanly with a one-line regex.

comparing the two agents

The point of running both is to see where they diverge — agents that produce the same answer on easy tasks can still differ wildly on the path they take. A few lenses to apply when reading a session:

01tool-call grain

How many discrete reads / edits / shell invocations does each agent make? One might read three files and rewrite one; the other might read one and make ten small edits. Finer grain is often slower but recovers from mistakes more locally.

02plan visibility

Does the agent state a plan before acting, or act and then summarize? Stated plans are easier to interrupt; implicit plans are faster but harder to redirect mid-task.

03recovery from being wrong

Make one agent guess at something it can't know (e.g. a function signature you haven't shown it). Watch how it reacts when reality contradicts the guess. Some double down; some retreat and re-read; some ask. The recovery shape is more revealing than the failure itself.

04prompt-following vs latitude

Give a slightly-underspecified task. Does the agent execute literally on what you said, or fill the gaps with its own judgment? Both can be right; the question is which you want when. Side-by-side makes the difference visible in a way solo runs don't.

05final diff shape

Once both are done, diff what they actually committed. Sometimes the transcripts look similar but the diffs are wildly different. Sometimes the transcripts diverge but converge on equivalent code. Both are worth knowing.

operational verbs

# list session artifacts
$ ls ~/.agent-multiplex/sessions/<id>/
manifest.json   claude.log   gemini.log

# replay a transcript with timestamps stripped
$ cat claude.log | perl -pe 's/\x1e\d+\x1e//g'

# diff each agent against the base branch
$ git -C <repo> diff main..mux/claude-<timestamp>
$ git -C <repo> diff main..mux/gemini-<timestamp>

# diff the two agents directly
$ git -C <repo> diff mux/gemini-<timestamp>..mux/claude-<timestamp>

good first comparisons

Tasks where divergence is likely and instructive:

  • Underspecified refactor — "Make this function easier to test" on a non-trivial function. Tests the latitude vs literalism axis.
  • Failing test — Hand them a failing unit test and the file it tests. The recovery path differs sharply across agents.
  • Same prompt, dirty repo — Run with uncommitted changes already in the base branch. Watch which agent notices.
  • Build error you can fix two ways — A type error with either an upstream fix or a downstream cast. Which one each agent picks tells you something about its priors.

troubleshooting

node-pty fails to build You're missing build tools. macOS: xcode-select --install. Linux: apt install build-essential python3. Then rm -rf node_modules and npm install again.
Both panes show exited (127) PATH was sanitized by npm and the agent binaries aren't visible to the spawned subprocess. The server augments PATH with ~/.local/bin, ~/.npm-global/bin, /opt/homebrew/bin, and the usual system dirs. If your CLI lives somewhere else, symlink it into one of those, or set PATH explicitly in the shell where you launch npm run dev -w backend.
UI shows backend not running Make sure npm run dev -w backend is running and curl localhost:4040/api/health returns {"ok":true}. The hosted page polls every 4 seconds.
Worktrees pile up after a crash If the backend dies mid-session, the worktrees outlive it. Clean up: git worktree list, then git worktree remove --force <path> for each -mux-* entry. Closing a session does not delete the branches either; drop with git branch -D mux/<agent>-<timestamp>.

limits worth naming

  • Backend binds to 127.0.0.1. No authentication. Single-user, single-laptop.
  • PTYs die with the backend process. No daemon, no resume across restarts.
  • API keys travel from the hosted page through your browser to your local backend. They never reach Railway. Verify in DevTools network panel — POSTs go to localhost:4040, not *.railway.app.
  • The harness creates real git branches in your repo. They survive session close until you delete them.
